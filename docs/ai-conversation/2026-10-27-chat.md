# Task: scaffold the repository for an encrypted file-storage web app

You are setting up the initial structure ("bones") of a Go web application for a university cryptography assignment built by a team of four. Your job on this branch (`chore/scaffold`) is ONLY the skeleton: project layout, configuration, Docker setup, database and storage clients, models, stubbed interfaces, stubbed HTTP routes, CI, and documentation. Do NOT implement the real cryptography, authentication, or file pipeline. Teammates will build those on separate feature branches against the interfaces you define here.

## Goal

A web application where users log in with a username and password and can store, then retrieve in decrypted form:
1. Private personal data (as defined by GDPR / Indonesia's UU PDP: name, NIK, date of birth, address, phone, email), stored in MongoDB
2. An ID card image
3. Documents (PDF, DOC/DOCX, XLS/XLSX)
4. Video files

All stored data must be encrypted with each of three algorithms: AES, DES, and RC4. Every upload is stored three times, once per algorithm, so the team can compare running time and ciphertext between ciphers. The final deliverable includes a report analysing those differences, so performance measurement is a first-class feature, not an afterthought. The program must be bug-free, so correctness and tests matter more than extra features.

## Tech stack (fixed, do not substitute)

- Language: Go, latest stable version (1.24 or newer, since we use `crypto/hkdf` from the standard library)
- HTTP: `github.com/gin-gonic/gin`, using `gin.New()` with explicit middleware, release mode in production, and `SetTrustedProxies(nil)`
- Validation: Gin binding tags (go-playground/validator) for all form and JSON input
- Database: MongoDB via `go.mongodb.org/mongo-driver/v2`
- Object storage: MinIO via `github.com/minio/minio-go/v7`
- Sessions (to be implemented later): `github.com/gin-contrib/sessions` with a MongoDB-backed store. Check which MongoDB driver version its store depends on. If it requires the v1 driver while we use v2, stop and tell me before adding both drivers.
- Frontend: server-rendered `html/template` + htmx (loaded from a CDN), embedded into the binary, no separate frontend service
- Password hashing (to be implemented later): `golang.org/x/crypto/argon2`
- Deployment: Docker + Docker Compose for every service
- No Keycloak or any external identity provider

## Cryptographic design (for context; implement only the interfaces and stubs)

- AES-256 and DES both use CTR mode. RC4 is used as a native stream cipher. All three are exposed through Go's `cipher.Stream` so a single streaming code path handles every algorithm.
- Every file gets fresh random per-algorithm data keys (DEKs), a fresh random IV (16 bytes for AES, 8 bytes for DES), and a separate HMAC-SHA256 key. Encrypt-then-MAC over the ciphertext.
- DEKs are wrapped (encrypted) with a master key (KEK) loaded from the environment, and stored in MongoDB alongside the file metadata. The master key is never stored in the database or committed to the repo.
- Downloads verify the HMAC first, then decrypt (two passes over the stored object).
- Files are streamed (`io.Reader` / `io.Pipe`) end to end, never fully loaded into memory, because videos can be large.

Only `internal/crypto` exports a shared interface, because it is the team-wide contract.

Gin may be imported only in `handlers.go`, `middleware.go`, `routes.go`, and `internal/web`. Model, store, and service files must never import Gin. Handlers only parse input, call a service function that takes plain Go types, and write the response.

## User (2026-10-14 14:27 UTC)

for auth, how many methods are there? is it according to the encryption methods?

## Assistant

No skills needed. Checking the auth package to answer from the code.

## Assistant

> *tool: Bash* — Read the auth service and user model

## Assistant

There is one login method: username and password. It does not follow the three encryption methods, and that is deliberate.

**How auth works (`internal/auth/service.go`)**
- **Register:** the password is turned into an **Argon2id hash** with a random salt. Only that hash is stored, in `users.password_hash`, never the password itself.
- **Login:** the typed password is hashed the same way and compared with the stored hash using a constant-time comparison.
- **Session:** after login, a session cookie keeps the user signed in, stored in MongoDB.

**Why it isn't AES/DES/RC4**
- **Hashing is one-way; encryption is reversible.** AES, DES and RC4 are built to be decrypted. A password should never be recoverable, not even by us. Login only needs a "does it match?" check, and a hash does exactly that.
- **Leaked data stays protected.** If the database leaked and passwords were encrypted, anyone with the master key could decrypt every one of them. With Argon2id hashes, each password has to be guessed separately, and Argon2id makes every guess deliberately slow.
- **RC4 and DES are in the project only for comparison.** RC4 and DES are weak ciphers. They are there to benchmark against AES, not to protect accounts.

**Where the three algorithms do apply**

| Feature | AES / DES / RC4? |
|---|---|
| Auth (passwords) | No: Argon2id hash only |
| Uploaded files (`feature/file-storage`) | Yes: each file is stored encrypted under all three, and you pick one at download (`?alg=aes`) |
| Profile private data (`feature/private-data`) | Yes: each field is encrypted under all three |
| Benchmarks | Measure the speed of those three on files and fields |

So the `feature/auth` work is one register/login flow plus sessions. It has no per-algorithm variants.

for auth, what crypto methods are used

## Assistant

No skills needed. Auth uses five cryptographic primitives, and none of them are AES, DES or RC4: those three are only for files and private data.

| # | Primitive | Where | What it does |
|---|---|---|---|
| 1 | **Argon2id** (`golang.org/x/crypto/argon2`) | `internal/auth/password.go` | Hashes passwords: t=3, 64 MiB memory, 2 lanes, 32-byte output, stored as a PHC string |
| 2 | **CSPRNG** (`crypto/rand`) | `password.go`, `session.go`, `service.go` | 16-byte salt per password, 32-byte session token per login, random password for the dummy hash |
| 3 | **HMAC-SHA256** (`crypto/hmac` + `crypto/sha256`) | `session.go` (`sessionID`) | Stores `HMAC(SESSION_SECRET, token)` as the session ID, so the database never holds a usable cookie value |
| 4 | **Constant-time comparison** (`crypto/subtle.ConstantTimeCompare`) | `password.go` (`VerifyPassword`) | Compares the computed hash with the stored one without leaking, through timing, how many bytes matched |
| 5 | **Base64 encoding** (`encoding/base64`) | `password.go`, `session.go` | Encodes the salt, hash and token as text. This is encoding, not encryption, and adds no security. |

**Why each one**
- **Argon2id:** a password has to be checkable but never recoverable, so it's hashed, not encrypted. It's deliberately slow and memory-hungry (about 95 ms and 64 MiB per guess), which makes stolen hashes expensive to crack.
- **Salt:** two users with the same password get different hashes, which defeats precomputed rainbow tables.
- **Session token:** 256 random bits can't be guessed.
- **HMAC on the token:** if MongoDB leaks, the attacker sees only HMACs. Turning one back into a working cookie would require reversing HMAC or knowing `SESSION_SECRET`.
- **Constant-time compare:** prevents timing attacks on the hash comparison.
- **Dummy hash for unknown usernames:** a wrong password and an unknown user take the same time (95 ms vs 98 ms measured), so the response time doesn't reveal which usernames exist.

**Related protections that aren't cryptography**
- **CSRF:** `http.CrossOriginProtection` checks the `Sec-Fetch-Site` and `Origin` headers.
- **Cookie flags:** `HttpOnly`, `SameSite=Strict`, and `Secure` when `COOKIE_SECURE=true`.
- **Abuse limits:** rate limiting per IP, and at most 4 concurrent Argon2id hashes.

**How auth compares with the encrypted features**

| | Auth | Files / private data |
|---|---|---|
| Goal | Prove identity | Keep content confidential |
| Reversible? | No (one-way hash) | Yes (decrypt with the key) |
| Primitives | Argon2id, HMAC-SHA256, CSPRNG | AES-256-CTR, DES-CTR, RC4, HMAC-SHA256, AES-GCM key wrapping, HKDF |
| Key | `SESSION_SECRET` (for the session HMAC only) | `MASTER_KEY` (wraps the data keys) |

The full justification is in `docs/decisions.md` D26–D30, which feeds the "justify your decisions" part of the report.

Yes. Every piece of private data and every file is encrypted with all three algorithms (AES-256, DES and RC4), so each one is stored as three separate encrypted copies. The two kinds of data go to different places: text data is stored encrypted in **MongoDB**, and files are stored encrypted in **MinIO**. Only the files ever reach MinIO. One caveat: the file part exists only on your local `feature/file-storage` branch until you push and merge it.

## What is encrypted, and where it goes

| Data | Encrypted with | Stored in |
|---|---|---|
| Private data: full name, NIK, date of birth, address, phone, email | AES, DES and RC4, so 3 copies of each field | MongoDB, `profiles` collection |
| Files: ID card image, documents, videos | AES, DES and RC4, so 3 objects per file | MinIO, bucket `securestore` |
| Original filename | AES, DES and RC4 | MongoDB, `files` collection |
| Keys for each copy | Locked with the master key (AES-256-GCM) | MongoDB, next to each copy |
| Password | **Hashed** with Argon2id, not encrypted (it never needs to be decrypted) | MongoDB, `users` |

## The shared encryption step (`internal/crypto/envelope.go`)

Each time anything is encrypted with one algorithm, the code does this:

1. **Make new random keys** with `crypto/rand`, so no key is ever reused. Each copy gets:
   - a data key: 32 bytes for AES, 8 for DES, 32 for RC4;
   - a separate 32-byte integrity key (for the tag in step 3);
   - an IV: 16 bytes for AES, 8 for DES, none for RC4.
2. **Encrypt in 32 KiB chunks.** AES and DES run in CTR mode and RC4 runs as a stream cipher, so the ciphertext is exactly as long as the plaintext.
3. **Compute an integrity tag** (HMAC-SHA256) over the ciphertext as it is produced.
4. **Lock both keys** with a key derived from the `MASTER_KEY` in `.env`, using AES-256-GCM.
5. **Store the details needed to decrypt later** (algorithm, IV, the locked keys and the tag) next to the ciphertext. The master key itself is never stored.

## Text data: browser → MongoDB → browser

**Save (`POST /profile`)**
1. The form fields are checked first, for example the NIK must be 16 digits.
2. Each field is encrypted 3 times, once per algorithm, with the step above.
3. MongoDB stores ciphertext plus the decryption details for every field. It also stores a keyed hash of the NIK, so a duplicate NIK can be rejected without keeping the NIK in plaintext.

**View (`GET /profile?alg=aes|des|rc4`)**
1. The page loads the copy for the algorithm you picked.
2. It checks the tag first. If the data was changed, you get an error page and nothing is decrypted.
3. Only then are the fields decrypted and shown.

## File data: browser → MinIO

When you upload (`POST /files`):

```text
browser ── multipart stream ──► handler
                                  │ reads the first 512 bytes: checks extension + content, size limit
                                  ▼
                       one read of the plaintext
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
               AES-CTR        DES-CTR          RC4      (in parallel)
                    ▼             ▼             ▼
            MinIO <user>/<file>/aes   …/des   …/rc4
                                  │
                                  ▼  only after all 3 are stored
            MongoDB: record with the filename encrypted 3×, the 3 sets of decryption details, size, type
```

- **Memory use:** the file is read once and passed to all three encryptions at the same time. It is never held fully in memory or written to disk: a 300 MiB video used at most 124 MiB of memory.
- **No plaintext stored:** MinIO only ever receives ciphertext. Object names contain only IDs, never the filename.
- **Failures:** if any step fails (a cipher, MinIO, MongoDB, or the client disconnecting), the copies already written are deleted and no record is saved.

## File data: MinIO → browser

When you download (`GET /files/:id/download?alg=aes`):

1. MongoDB is checked for the record. It must belong to you, otherwise you get 404.
2. The `aes` object is opened in MinIO.
3. **First pass: integrity check.** The whole object is read and its tag is checked. Nothing has been sent to the browser yet, so a tampered file returns **422** and no bytes.
4. **Second pass: decrypt.** The object is read again from the start, decrypted chunk by chunk, and streamed straight to the browser. The file is sent as a download (never opened in the browser) with `no-store` caching.

**Why two passes:** decrypting during the first read would send unchecked plaintext to the browser before tampering could be detected. The cost is that MinIO reads each object twice per download.

**Timing records:** each encrypt and decrypt also saves a timing record to the `benchmarks` collection. The future Benchmarks page and the report will use these.

Yes, that's on purpose, and it's the evidence that the encryption works. If you could open the images in MinIO, anyone with access to the storage server could too.

**What you're seeing**
- **The names aren't encrypted; they're IDs.** Each object is stored as `<user id>/<file id>/<aes|des|rc4>`, using the MongoDB IDs (24 hex characters). The real filename isn't used because filenames are often personal data, like `KTP_Budi_Santoso.jpg`. The original name is stored encrypted in MongoDB instead (`files.file_name`, again with AES, DES and RC4 copies).
- **The three objects are the same file, encrypted three ways.** Every upload is encrypted with AES-256, DES and RC4, as the assignment requires. Each copy uses its own random key and IV.
- **The contents are ciphertext,** so they can't be opened. In CTR mode and with RC4 the ciphertext is exactly the same size as the original, but every byte is scrambled. Even the JPEG or PDF header that a viewer looks for is gone, so MinIO's preview and image viewers see random bytes.

**How to see the image again**
Only through the app, as the logged-in owner. Go to **My application → 2. Documents**, then click **AES**, **DES** or **RC4** on that document. The app:
1. checks the HMAC of that copy;
2. decrypts it with that copy's key, unwrapped with the master key;
3. sends you the original file.

All three buttons give a byte-identical file.

**To match a MinIO object to its file**, look it up in MongoDB:
```bash
M 'printjson(db.files.findOne({"variants.aes.object_key": "<paste the object path>"}, {kind:1, slot:1, size:1, mime_type:1}))'
```
That shows the slot (e.g. `ktp`), the type and the size. The filename stays encrypted there too.

**For the report**, this is the "the storage server never sees plaintext" argument. A leaked MinIO bucket or backup reveals nothing usable without `MASTER_KEY`, which is kept outside both MongoDB and MinIO.
